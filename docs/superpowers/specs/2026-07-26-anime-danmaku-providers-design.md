# 动漫弹幕来源首批扩展设计

## 背景

`atv-player` 当前内置腾讯、优酷、B站、爱奇艺、芒果、搜狐、咪咕和人人八个弹幕来源。它们以国内综合视频平台为主，对动画、台湾地区内容和由社区维护的动画条目覆盖不足。

本轮参考本地 `/home/harold/workspace/danmu_api` 的来源实现，首批增加弹弹Play、巴哈姆特和 Animeko。运行时仍由桌面客户端直接装配独立 provider，不要求用户部署或配置 `danmu_api` 服务。

## 目标

- 增加 `dandan`、`bahamut`、`animeko` 三个可独立搜索和解析的弹幕 provider。
- 搜索结果展开到具体剧集，并继续参与现有集数匹配、来源分组、历史偏好、手动切源和缓存恢复流程。
- 三个来源默认启用，同时允许用户在高级设置中逐一禁用。
- 单个来源超时、无结果或响应异常时不影响其他来源。
- 保持现有来源的顺序和默认选择行为；新来源追加在现有来源之后。

## 非目标

- 不部署、不嵌入、不代理整个 `danmu_api` 服务。
- 不移植韩剧TV、西瓜、乐视、埋堆堆、爱壹帆等第二批来源。
- 不实现多来源弹幕合并、跨源时间轴对齐或来源标签注入。
- 不改变通用候选排序权重、清洗规则或播放器弹幕渲染逻辑。
- 不把真实外部接口可用性作为自动化测试前提。

## 方案选择

采用三个独立原生 provider：

- `DandanDanmakuProvider`
- `BahamutDanmakuProvider`
- `AnimekoDanmakuProvider`

每个 provider 负责自己的搜索、作品详情/剧集展开、内部 URL 解析和弹幕格式转换，统一实现现有 `DanmakuProvider` 协议。相比统一的“动漫 provider”基类，这种设计更符合三个上游在认证、分页、节点降级和 payload 结构上的实际差异，也能让单源修改保持隔离。

不采用弹弹Play兼容聚合服务作为统一入口，因为它会把三个来源重新绑定到一个外部部署。公共代码只提取确实相同的轻量操作，例如安全数字转换或内部 URL 解析；不建立为未来来源预留的抽象层。

## Provider URL 与恢复语义

搜索结果使用稳定、可路由的内部 URL：

| 来源 | URL 格式 | 标识符 |
|---|---|---|
| 弹弹Play | `dandan://episode/{episodeId}` | 弹弹Play episode ID |
| 巴哈姆特 | `bahamut://episode/{videoSn}` | 巴哈姆特 videoSn |
| Animeko | `animeko://episode/{episodeId}` | Animeko episode ID |

`supports()` 只接受本 provider 的内部 scheme 和合法的非空标识符。`resolve()` 从 URL 重新取得标识符，而不依赖只存在于当前进程的搜索对象。这样用户选择结果写入缓存后，应用重启仍可路由到同一个 provider。

搜索结果的 `resolve_context` 可保留作品 ID、剧集 ID 和原始标题等诊断信息，但解析正确性不得依赖该字段。

## 弹弹Play数据流

1. 使用参考实现采用的弹弹Play兼容接口搜索动画条目。
2. 对少量高相关条目读取作品详情与剧集列表。
3. 只把有效剧集转换为 `DanmakuSearchItem`；候选名称由作品标题和“第 N 集/话 + 分集标题”组成。
4. 如果原始查询含明确集数，优先返回该集；没有明确集数时保留有限数量的剧集候选供现有服务排序。
5. 解析时请求 `/v2/comment/{episodeId}` 语义的评论数据，读取 `p` 中的时间、模式和颜色并映射为 `DanmakuRecord`。

弹弹Play接口地址作为 provider 内部常量集中管理。首版遵循参考项目当前使用的 `api.danmaku.weeblify.app/ddp/v1` 兼容入口，因此不需要用户申请 App ID；该入口是运行时外部依赖，其失效只使 `dandan` 返回失败，不阻断其他来源。后续如切换到带签名的官方入口，只修改该 provider。

## 巴哈姆特数据流

1. 对搜索词进行简体到繁体转换后调用巴哈姆特动画搜索接口；转换使用纯 Python 的 `opencc-python-reimplemented>=0.1.7`，不复制不完整的字符映射表。
2. 读取高相关作品的 `videoSn`，通过作品详情接口取得完整剧集列表。
3. 为每集生成 `bahamut://episode/{videoSn}` 候选，名称包含作品标题和明确集号。
4. 解析时调用巴哈姆特 danmu 接口；时间由十分之一秒转换为秒，位置 `0/1/2` 映射为滚动/顶部/底部，`#RRGGBB` 转为十进制颜色。

搜索、详情和弹幕请求使用参考项目已验证的移动端 User-Agent。简繁转换同时用于标题比较，避免简体查询被繁体结果误判为无关候选。转换依赖必须加入项目依赖和打包验证范围。

## Animeko 数据流

1. 使用 Bangumi V0 搜索接口定位动画 subject，限制动画类型并过滤低相关结果。
2. 通过 Animeko V2 节点读取 subject 的主线剧集；仅加入 `MAIN` 剧集，SP/OVA 不混入普通集号匹配。
3. 为每集生成 `animeko://episode/{episodeId}` 候选，名称包含作品中文名或主标题、集号和可用的分集标题。
4. 解析时访问 Animeko `/v1/danmaku/{episodeId}`，把毫秒时间转换为秒，把 `NORMAL/TOP/BOTTOM` 映射为 `1/5/4`，颜色 `-1` 归一化为白色。

Animeko 节点顺序与参考实现一致：Asia/Shanghai 环境优先 `api.animeko.org`，随后尝试 global、CN 和 openani 节点；其他时区优先 global。provider 记住最近一次成功节点，以减少后续无效等待。所有节点失败后抛出 Animeko 来源的解析错误。

搜索和详情分别设定候选数、分页数与请求超时上限。单次搜索不会无界翻页，也不会为所有模糊结果请求详情。

## 服务装配与设置

`create_default_danmaku_service()` 构造三个新 provider，并将默认顺序扩展为：

```text
tencent, youku, bilibili, iqiyi, mgtv, sohu, migu, renren,
dandan, bahamut, animeko
```

追加顺序保留已有来源的排名和默认选择行为。新来源仍由现有有界并发搜索机制调度。

`DANMAKU_SOURCE_PREFERENCES` 增加：

- `dandan`：弹弹Play
- `bahamut`：巴哈姆特
- `animeko`：Animeko

因此三个开关自动进入高级设置，并沿用现有 `disabled_danmaku_provider_ids` 持久化格式。老配置不包含这些 ID，升级后默认启用；用户禁用后，搜索和解析均跳过对应 provider。

## 错误处理

- 搜索阶段的网络错误、非 JSON 响应、字段缺失或无匹配条目返回空列表，由 `DanmakuService` 继续收集其他来源。
- 作品详情中的单条异常记录被跳过，不因一个损坏剧集丢弃全部有效候选。
- 解析阶段区分“合法响应但评论为空”和“请求或 payload 解析失败”。前者触发现有空弹幕语义，后者抛出包含来源名称的 `DanmakuResolveError`。
- 所有时间值限制为非负数；空文本、非法时间、非法颜色和缺失标识符的记录被跳过。
- Animeko 仅在当前节点失败或 payload 无效时切换节点；合法空列表视为成功的空弹幕，不重复轰炸全部节点。

## 性能边界

- 每个 provider 只展开有限数量的高相关作品。
- 明确集数查询在 provider 内优先缩减候选，但最终正确性仍由通用集数匹配保障。
- Animeko 搜索和详情分页都有硬上限。
- provider 不创建无界线程池；跨 provider 并发继续由现有 `_concurrency` 工具控制。
- 不新增跨 provider 的全局缓存。Animeko 可在 provider 内维护小型、短时的详情/健康节点缓存，且必须设置容量和有效期上限。

## 测试设计

为三个 provider 分别创建测试文件，所有网络响应通过依赖注入提供，不访问真实网络。

### Provider 单元测试

- 搜索结果能从作品展开为具体剧集，名称和内部 URL 正确。
- 明确集数查询优先返回对应集，缺失目标集时保留合理降级结果。
- `supports()` 接受自己的内部 URL 并拒绝其他 scheme 或空 ID。
- 弹幕时间、位置、颜色和文本正确转换为 `DanmakuRecord`。
- 空评论返回空记录；非法记录被跳过。
- 搜索异常返回空列表；解析异常产生带来源名称的错误。
- Animeko 首选节点失败后使用下一节点，并记住成功节点。
- Animeko 合法空评论不继续请求其他节点。
- 巴哈姆特使用繁体搜索词并能保留与简体查询对应的结果。

### 集成与设置测试

- 默认服务顺序在现有八个来源后追加 `dandan`、`bahamut`、`animeko`。
- 禁用任一新来源后，它不出现在 `provider_order`，也不参与搜索或解析。
- 来源分组显示“弹弹Play”“巴哈姆特”“Animeko”。
- 高级设置创建三个开关，保存后正确更新 `disabled_danmaku_provider_ids`。
- 稳定内部 URL 能在只有缓存结果、没有原搜索对象时完成解析路由。

### 验证命令范围

实现阶段先按测试驱动逐个运行新增 provider 测试，再运行：

- 弹幕服务测试
- 来源偏好与高级设置相关测试
- 完整测试集
- Ruff 和 Pyright
- 打包或依赖导入检查，确认简繁转换依赖可由应用运行环境加载

自动化测试通过后，可对三个来源各执行一次只读真实接口冒烟测试。真实接口状态记录在交付说明中，但网络波动不进入自动化测试判定。

## 验收标准

- 三个来源均能从标题搜索得到具体剧集候选。
- 用户切换到任一来源后可解析并加载统一 XML 弹幕。
- 应用重启后，已缓存的内部来源 URL 仍能路由到正确 provider。
- 三个来源均可在高级设置独立禁用。
- 一个新来源失败时，现有来源和另外两个新来源仍能正常返回。
- 现有八个来源的默认顺序、匹配、选择和解析测试无回归。

## 已知运行时风险

- 弹弹Play兼容入口、巴哈姆特接口和 Animeko 节点均为客户端外部依赖，可能限流、改版或停止服务。
- 巴哈姆特可能存在区域限制；网络代理继续由应用现有 HTTP 注入层处理，不在 provider 内建立另一套代理配置。
- Animeko 与 Bangumi 的条目或集号可能短时不同步；本轮不实现跨数据库集号校正。
- 上游 payload 改版应只影响对应 provider；结构校验和来源级错误用于避免故障扩散。
