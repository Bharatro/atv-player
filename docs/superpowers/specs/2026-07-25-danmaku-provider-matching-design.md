# 弹幕 Provider 扩展与匹配优化设计

## 背景

`atv-player` 当前原生支持腾讯、优酷、B站、爱奇艺、芒果、搜狐、咪咕和人人八个弹幕来源。现有实现已经具备并发搜索、来源选择、历史偏好、搜索与 XML 缓存、弹幕渲染和按来源禁用等能力，但候选过滤与排序规则分散在 `service.py`、`utils.py` 和各 provider 内部。标题、季集、年份和时长信息没有统一的数据模型，导致同名作品、翻拍作品、续作和剧情式剧集标题容易误匹配或漏匹配。

本次参考本地 `/home/harold/workspace/danmu_api` 的 source 实现和匹配经验，但保持 `atv-player` 原生直连：运行时不依赖用户部署 `danmu_api`，也不调用其聚合接口。

工作区已有的腾讯同名剧展开、剧情式集标题匹配和非法 XML 控制字符修复视为设计基线，后续实现必须保留并纳入回归测试。

## 目标

- 原生新增弹弹Play、Animeko、乐视、西瓜和韩小圈五个弹幕 provider。
- 统一标题、别名、年份、季号、集号、媒体类型、时长、来源 URL 和历史偏好的匹配逻辑。
- 自动加载采用保守策略：只有高置信候选可以自动选择，中置信候选仅供手动选择。
- 保持现有 provider 协议和普通 Spider 播放入口兼容。
- 保持单源加载模型；本次不实现跨 provider 弹幕合并。
- 保持搜索有界并发，单个 provider 失败不影响其他来源。

## 非目标

- 不内置或部署 `danmu_api` 服务。
- 不移植巴哈姆特、埋堆堆或爱壹帆 provider。
- 不实现跨来源时间轴对齐、去重或弹幕合并。
- 不进行与弹幕匹配无关的播放器或元数据架构重构。
- 不要求所有旧 provider 在一次改动中补齐全部结构化元数据；允许渐进迁移。

## 方案选择

采用“统一匹配引擎 + 原生 provider 适配器”。

未采用以下方案：

- Provider 内部分别匹配：初期移植较快，但规则会重复和分叉，同一标题在不同来源可能得到矛盾判断。
- 内置完整聚合管线：长期适合多源合并，但会大幅改动现有接口、缓存和 UI，超出本次范围。

## 总体架构

新增 `atv_player.danmaku.matching`，把散落的标题规范化、硬性约束、置信度评分、拒绝原因和排序规则集中管理。`DanmakuService` 只负责编排 provider、收集候选、调用匹配器、分组和选择默认来源。各 provider 只负责搜索、作品与剧集展开、来源身份解析和弹幕格式转换。

数据流如下：

```text
播放条目与刮削元数据
        ↓
构建 DanmakuMatchContext
        ↓
并发搜索原生 providers
        ↓
规范化 DanmakuCandidateMetadata
        ↓
硬性排除 → 证据评分 → 置信分级 → 去重排序
        ↓
高置信自动加载 / 中置信仅供手选 / 低置信丢弃
```

### 核心模型

`DanmakuMatchContext` 表示一次搜索的用户意图和可用媒体信息：

- 主查询标题
- 可靠别名列表
- 年份
- 季号
- 集号
- 媒体类型
- 当前视频时长
- 播放来源 URL
- 是否为用户手动覆盖的搜索词

`DanmakuCandidateMetadata` 表示 provider 返回的结构化候选身份：

- provider 与稳定作品、剧集 ID
- 展示标题与父作品标题
- 别名列表
- 年份
- 季号与集号
- 媒体类型
- 时长
- 可解析 URL 与 provider 私有解析上下文

`DanmakuMatchResult` 表示统一匹配器的判断：

- 分数
- `high`、`manual` 或 `rejected` 置信等级
- 命中证据
- 拒绝原因

现有 `DanmakuSearchItem` 和 `DanmakuSourceOption` 增加可选结构化字段，并保留现有字段和默认值。旧 provider 的 `search(name, original_name)` 继续可用；支持结构化请求的 provider 通过可选能力接收 `DanmakuMatchContext`。服务层负责能力检测，不要求外部调用方或测试 fake provider 同步升级。

## Provider 设计

所有新增 provider 都使用应用注入的 HTTP 客户端，服从全局代理、统一 User-Agent 策略、超时和错误模型。运行时不请求 `danmu_api` 或其转发服务。

### 弹弹Play

- 直连弹弹Play官方开放接口，搜索作品并获取作品详情、标题别名和剧集列表。
- 使用官方作品 ID 和 episode ID 作为稳定身份。
- 通过作品标题、别名、年份和类型选择父作品，再按目标季集选择 episode。
- 直接通过官方评论接口拉取弹幕并转换为 `DanmakuRecord`。
- 若官方接口要求签名，签名和请求头构造完全封装在 provider 内。

### Animeko

- 通过 Bangumi/Animeko 的公开节点搜索作品、读取关联信息和剧集列表。
- 中文名、中文别名优先，日文原名只作为补充证据，不能单独覆盖明确的年份或季号冲突。
- 通过 episode ID 从 Animeko 弹幕节点读取弹幕。
- 维护进程内节点健康顺序；请求失败或返回畸形数据时轮换节点。

### 乐视

- 使用乐视搜索页搜索作品，从 TV、动漫、短剧或电影详情页提取作品和剧集。
- 以乐视 media ID 和 video ID 作为稳定身份。
- 从播放页读取时长，按五分钟构造弹幕分段。
- 使用 `hd-my.le.com` 弹幕接口有限并发获取 JSONP 分段，并规范化位置、颜色和时间。

### 西瓜

- 使用西瓜移动搜索与详情页识别作品合集、剧集和单个视频。
- 以 album/item ID 作为稳定身份，严格区分合集剧集与普通短视频。
- 根据详情时长构造五分钟分段，调用 `ib.snssdk.com` 弹幕接口。
- 明显短于目标长视频的单个片段不能成为自动候选。

### 韩小圈

- 封装 App 和 TV 两套搜索、详情、剧集和弹幕接口。
- 主线路失败时降级到备用 host 或 TV 接口。
- 两条线路视为同一个 provider 的容错路径，不做跨线路弹幕合并。
- 使用节目和剧集 ID 作为稳定身份，并保留来源线路信息供解析恢复。

### Provider 通用约束

- 搜索、详情和解析分别设置短超时。
- 单 provider 的搜索或解析异常被隔离，不能终止整体搜索。
- 分段弹幕最多同时执行八个网络请求。
- 返回稳定来源 ID、父作品身份和结构化剧集信息，不把临时搜索 URL 当作唯一身份。
- 新 provider 加入高级设置，可分别启用或禁用。
- provider 搜索顺序按媒体类型调整。动漫在同等证据下优先 B站、弹弹Play和 Animeko；真人影视仍优先腾讯、优酷、爱奇艺和芒果。顺序只用于同分决胜，不直接产生高置信匹配。

## 匹配设计

匹配先执行硬性约束，再计算证据分数。硬性冲突不能被标题相似度、历史偏好或 provider 优先级抵消。

### 标题规范化

- 使用 Unicode NFKC 统一全半角字符。
- 统一大小写、空白和无语义标点。
- 生成简体与繁体变体。
- 只移除明确的画质、配音、版本和平台噪声标签。
- 在季集语义之外转换中文数字。
- 年份、季号、`Part` 和续作数字始终保留为独立特征，不盲目从标题删除。
- 短标题采用更严格阈值，不能仅凭一个或两个公共字符匹配。

### 硬性排除

以下任一明确冲突会拒绝候选：

- 双方集数已知且不同。
- 双方季号已知且不同。
- 双方年份已知且不同。
- 双方媒体类型明确，且电影、剧集、综艺类型互相冲突。
- 续作数字或 `Part` 明确冲突。
- 双方时长已知且触发下述时长硬冲突阈值。
- 没有父作品身份的候选标题与任一主标题或可靠别名均无有效关系。

未知字段不构成冲突，只会减少可获得的证据。

### 证据与排序

初始评分使用固定的 100 分制证据模型：

- 规范化主标题完全一致：50 分。
- 任一可靠别名完全一致：48 分；与主标题完全一致不重复累计。
- 有边界的包含关系或高质量字符相似：最高 30 分；不能与完全一致分重复累计。
- 集号准确一致：20 分。
- 季号准确一致：12 分。
- 年份准确一致：10 分。
- 媒体类型准确一致：8 分。
- 时长接近：最高 8 分。
- 播放 URL 与 provider 一致：5 分。
- 已验证的同作品历史偏好：5 分。

证据累计后总分封顶为 100 分。

Provider 顺序仅作为同分决胜。上述权重与阈值由表驱动测试固定，不允许 provider 自行放宽统一的自动加载门槛。

结果分为三级：

- `high`：至少 65 分、标题身份成立、所有已知季集约束一致，并且已知时长没有超出近似范围；可成为默认项并自动加载。
- `manual`：至少 35 分且无硬冲突，或者分数达到 65 但缺少父作品身份等必要自动匹配条件；显示在弹幕源对话框中，不自动下载。
- `rejected`：低于 35 分、存在硬冲突或标题关系过弱；不展示。

“标题身份成立”要求主标题或可靠别名完全一致；也可由高质量标题相似加至少两项季号、集号、年份、媒体类型或近似时长证据共同成立。单独的模糊相似度、来源顺序或历史偏好不能满足该条件。

时长规则按比例和绝对差值共同判断：

- 差值不超过 `max(180 秒, 目标时长的 10%)` 时获得 8 分。
- 差值不超过 `max(300 秒, 目标时长的 20%)` 时获得 4 分。
- 双方时长已知但超出上述近似范围时，候选最高只能进入 `manual`。
- 对至少 20 分钟的目标视频，候选短于目标的 55%，或双方差值超过 `max(900 秒, 目标时长的 50%)` 时构成硬冲突。
- 任一时长未知时不加分、不拒绝，也不单独阻止由标题与季集强证据形成的 `high`。

剧情式剧集标题必须关联父作品身份。例如腾讯候选“第十三集 + 剧情副标题”可以依靠父作品标题和 episode 13 成为高置信候选；旧 provider 只返回该剧集标题而没有父作品信息时，最多进入手选等级，不能仅凭集号自动匹配。

### 搜索变体

每个 provider 最多使用三个搜索变体：

1. 清洗后的主标题。
2. 一个可靠别名。
3. 去除明确季号后的回退标题。

搜索从高质量变体开始；已有高置信结果时不继续扩大模糊搜索。变体需要去重，并受 provider 自身能力限制，避免请求数量随别名线性增长。

## 上下文来源与兼容

`PlayItem` 增加带默认值的弹幕匹配字段：别名、年份、季号、集号和媒体类型。能够提供结构化刮削结果的播放入口逐步补齐这些字段；普通 Spider、Emby、Jellyfin 等旧入口仍可使用现有标题、原始标题、类型字段和播放列表位置推断上下文。

用户手动修改搜索标题后，输入标题成为新的主标题。旧别名、旧年份和自动清洗结果不能压过用户输入。手动指定 provider 会缩小搜索范围，但仍执行明确的季集硬性约束。

## 缓存与历史偏好

搜索缓存升级版本。缓存键的上下文指纹包含：

- 规范化主标题
- 年份、季号、集号和媒体类型
- 启用的 provider 集合
- 匹配规则版本
- 播放来源标识

旧搜索缓存因版本变化自然失效。缓存内容增加候选结构化元数据、置信等级和匹配证据；恢复缓存后仍使用当前上下文重新评分，不能直接信任旧默认项。

XML 缓存绑定 provider 和稳定 episode ID，保留现有三天有效期。搜索标题和页面 URL 可以继续作为兼容回退键，但恢复后必须验证目标集数。

历史偏好以“规范化作品身份 + 可用年份 + 季号”为 series key，并保存 provider、稳定作品 ID 和最近选中的来源信息。偏好只作为辅助证据；应用到新一集前必须重新验证候选季集。旧格式偏好只有在当前匹配器验证通过后才能复用。

## UI 行为

高级设置的弹幕源列表增加弹弹Play、Animeko、乐视、西瓜和韩小圈开关。

播放器“弹幕源”对话框保持现有 provider/候选双栏布局。候选行增加简短置信标记和关键原因，例如：

- `高｜标题、S1E13、时长一致`
- `手选｜标题一致、年份未知`

只有 `high` 候选可以成为 `default_option_url`。如果只有 `manual` 候选，对话框仍展示结果，但保持默认来源为空，不自动下载。用户手动加载中置信候选后保存历史偏好，但偏好不能绕过后续剧集的硬性校验。

## 错误处理与可观测性

- 区分搜索空结果、接口响应变化、请求超时、解析空弹幕和不支持 URL。
- 日志记录 provider、阶段和简短错误原因，不记录密钥、签名或完整敏感请求头。
- 多节点 provider 在当前进程维护最后一次健康节点；所有节点失败后回到默认顺序。
- 单 provider 失败只影响该来源，其余 provider 继续返回候选。
- provider 搜索仍使用项目现有有界并发工具；新增来源不能使整体等待时间退化为逐源串行之和。

## 测试策略

实现使用测试驱动。CI 中所有 provider 测试使用固定响应样本和 fake HTTP 客户端，不依赖真实网络。

### 匹配器测试

表驱动测试至少覆盖：

- 同名翻拍作品的年份冲突。
- 第一季、续作、`Part 2` 和特别篇。
- 正确剧集与相同集数的其他作品。
- 剧情式集标题与正确父作品关联。
- 简繁体、日文原名和可靠别名。
- 电影正片与预告、花絮、速看。
- 综艺日期、期数和上下篇。
- 短标题和噪声标签。
- 未知时长和明显时长冲突。
- `high`、`manual`、`rejected` 边界及解释文本。

### Provider 契约测试

每个新增 provider 独立覆盖：

- 搜索结果规范化。
- 作品与剧集展开。
- 正常弹幕转换。
- 空响应、畸形响应和关键字段缺失。
- 超时与备用节点降级。
- 分段请求数量和最大并发限制。
- `supports()`、稳定 ID 和解析上下文恢复。

### 集成与回归测试

- 五个新 provider 的注册、标签、媒体类型优先级、禁用设置和手动筛选。
- 搜索缓存上下文隔离、规则版本失效和恢复后重评分。
- 中置信候选不自动加载。
- 手动选择保存偏好，下一集重新验证。
- 腾讯同名剧展开和剧情式集标题。
- 非法 XML 控制字符清洗。
- 现有八个 provider、播放器选源、预下载和缓存恢复行为。

## 验收标准

- 原有弹幕测试和新增测试全部通过。
- 五个新增 provider 可在高级设置和弹幕源对话框中启用、禁用和手动筛选。
- 自动加载只选择高置信候选。
- 明确年份、季号、集号或媒体类型冲突的候选不会被自动或历史偏好选中。
- 单 provider 故障不会阻断其他来源。
- 搜索保持有界并发，不因新增来源退化为逐源串行。
- 固定样本测试通过后，对五个新增 provider 做少量真实接口冒烟测试；网络不可用或接口受地域限制时明确记录结果，真实网络测试不替代固定样本测试。

## 实施顺序约束

后续实施计划应按以下依赖顺序拆分：

1. 建立匹配上下文、候选元数据和匹配器测试。
2. 接入服务、缓存、历史偏好和 UI 的置信语义。
3. 逐个新增 provider 及其固定样本测试。
4. 补齐媒体入口上下文和旧 provider 的关键父作品身份。
5. 运行回归测试和真实接口冒烟测试。

每一步必须保持旧 provider 可用，并避免覆盖工作区已有的弹幕修复。
