# 优酷剧集弹幕搜索修复设计

## 背景

播放器以 `悬案 4集` 搜索弹幕时，优酷来源没有返回第 4 集正片，反而显示了大量预告、看点和推荐视频。

线上响应确认了两个根因：

- 优酷搜索接口现在将集数放在 `displayName` 或 `showVideoStage`，`title` 只包含单集副标题。现有解析只读取 `title`，因此得到 `悬案 矢量` 等不含集数的名称，随后被第 4 集精确匹配过滤。
- 详情页回退逻辑扫描页面中所有带 `aria-label` 的链接，把推荐内容误当成选集；同时新版页面的完整选集位于 `window.__INITIAL_DATA__`，旧 HTML 链接解析无法可靠取得这些正片。

## 目标

- `悬案 4集` 在优酷来源中命中 `https://v.youku.com/v_show/id_XNjUxODE2NjYyOA==.html`。
- 优酷剧集候选名称包含明确集数，例如 `悬案 第4集 专线`。
- 优酷剧集候选只保留正片，过滤预告、剧集看点和推荐视频。
- 保留对旧版优酷选集 HTML 的兼容回退。

## 非目标

- 不修改全局弹幕排序和精确集数匹配规则。
- 不修改优酷弹幕下载、鉴权或分段请求逻辑。
- 不调整其他弹幕 provider。

## 方案

### 搜索响应

解析 `componentMap["1035"].data` 时，优先从 `showVideoStage` 或 `displayName` 取得集数，并与 `title` 组合为单集名称。若 `title` 已经包含同一集数，则不重复添加。只有集数可识别且没有预告、看点标记的条目才能作为搜索接口候选。

搜索响应仍可提供首批候选和详情页入口，但不假设该列表包含全部剧集。以当前《悬案》响应为例，搜索接口只返回部分选集，因此第 4 集必须由详情页完整选集补齐。

### 详情页结构化解析

从详情页脚本中的 `window.__INITIAL_DATA__ = {...}` 读取 JSON，遍历 `moduleList[].components[]`，仅处理选集组件：

- 组件 `type` 为 `10013`。
- 条目 `videoType` 为 `正片`。
- 条目 `stage` 可解析为正整数。
- `action_value` 或 `action.value` 中存在有效优酷视频 ID。

候选名称使用父级媒体标题、规范化集数和单集标题组合；URL 规范化为 `https://v.youku.com/v_show/id_<vid>.html`。预告、剧集看点以及其他组件中的推荐内容不会进入结果。

### 兼容回退

当页面没有有效的 `window.__INITIAL_DATA__` 选集时，继续支持旧版 HTML，但只解析 `box-anthology-item` 中集数可识别且没有预告、看点标记的选集链接，不再扫描页面全部 `aria-label` 链接。

结构化详情结果对所属剧集具有权威性：只要成功取得该剧集的正片选集，就不再追加该剧集搜索接口中的未匹配候选。搜索接口中与结构化结果 URL 相同的条目只用于补充时长等已有元数据。详情结构不存在时才使用受限的旧版 HTML 或搜索接口候选。

## 错误处理

- `window.__INITIAL_DATA__` 缺失、JSON 解析失败或选集为空时，不中断整个 provider 搜索，转入旧版 HTML 回退。
- 单个无效条目直接跳过，不影响同组件中的其他正片。
- 详情页请求失败时保留搜索接口已有候选，延续当前降级行为。

## 测试

- 搜索接口的 `title="专线"`、`displayName="4"` 或 `showVideoStage="4"` 生成包含第 4 集的候选名称。
- 详情页 `window.__INITIAL_DATA__` 能解析完整正片选集，并生成第 4 集目标 URL。
- 同一选集中的 `videoType="预告片"` 和 `videoType="剧集看点"` 被过滤。
- 其他组件中的推荐条目不进入候选。
- 结构化选集成功后，搜索接口中的同集预告不会被重新合并进结果。
- 旧版 `box-anthology-item` HTML 仍可解析，而普通 `aria-label` 推荐链接被忽略。
- provider 与弹幕服务层回归测试证明 `悬案 4集` 最终只保留精确第 4 集候选。

## 验收标准

弹幕源对话框以媒体标题 `悬案`、集数 `4集` 重新搜索后，优酷组出现 `悬案 第4集 专线`，加载地址为用户提供的第 4 集 URL；优酷组不再出现截图中的资讯、预告和推荐视频噪声。
